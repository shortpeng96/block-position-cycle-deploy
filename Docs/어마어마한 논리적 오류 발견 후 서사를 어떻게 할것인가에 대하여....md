# Block Position Cycle 프로젝트 분석 구조 재검토 기록

## 1. 분석 과정에서 확인한 핵심 문제

프로젝트를 진행하면서 데이터의 의미와 생성 구조에 대해 두 차례 중요한
해석 수정이 있었다.

이 과정은 단순한 오류 수정이라기보다, 분석을 진행하면서 데이터의 의미와
변수 간 관계를 다시 검증하고 분석 구조를 재설계한 과정으로 정리할 수
있다.

------------------------------------------------------------------------

## 2. 1차 해석 수정: Block Position Cycle의 의미

### 초기 해석

프로젝트 초기에는 `Block Position Cycle`을 실제 작업 결과로 발생한
처리기간 또는 실제 공기와 유사한 값으로 해석했다.

이에 따라 Block의 여러 특성을 이용하여 실제 처리기간을 예측하는 일반적인
회귀분석 문제로 접근했다.

### 문제 인식

데이터셋의 구조와 관련 자료 및 선행연구를 추가로 검토하면서
`Block Position Cycle`은 스케줄링 결과로 생성되는 값이 아니라, 스케줄링
이전에 이미 각 Block에 주어진 기준 처리기간이라는 점을 확인했다.

정확한 산정식과 원천은 공개 자료만으로 확인하기 어렵지만, 해당 값은
스케줄링 알고리즘이 Block의 배치 및 일정을 결정할 때 사용하는 사전
정보에 가까운 것으로 판단했다.

### 수정된 해석

따라서 프로젝트에서는 `Block Position Cycle`을 다음과 같이 정의한다.

> **Block Position Cycle = 스케줄링 이전에 Block별로 주어진 기준
> 처리기간**

즉, 이를 실제 작업 이후 관측된 실적 공기와 동일하게 해석하지 않는다.

------------------------------------------------------------------------

## 3. 2차 해석 수정: 선택 Position의 변수 역할

### 기존 분석 구조

DDQN Scheduling Result를 Block과 Position을 연결하는 Mapping Table로
사용하여 다음과 같은 Master Table을 구성했다.

**Block 정보 + DDQN이 선택한 Position 정보 + Initial 정보**

이후 해당 변수들을 독립변수로 사용하여 `Block Position Cycle`을 예측하는
회귀분석을 진행했다.

구조는 다음과 같았다.

**Block 특성 + DDQN 선택 Position 특성 + Initial 관련 정보 → Block
Position Cycle**

기술적으로는 Block과 Position을 정상적으로 연결할 수 있었기 때문에
선택된 Position 특성을 자연스럽게 회귀모델의 독립변수로 활용했다.

------------------------------------------------------------------------

## 4. Streamlit 시각화 과정에서 발견한 문제

7가지 스케줄링 방법론의 결과를 Streamlit으로 시각화하는 과정에서 중요한
문제가 명확하게 드러났다.

동일한 Block이라도 스케줄링 방법론에 따라 서로 다른 Position이
선택되었다.

예를 들면 다음과 같은 구조다.

  항목                DDQN         EDDQN        SPT
  ------------------- ------------ ------------ ------------
  Block 특성          동일         동일         동일
  Scheduling Method   DDQN         EDDQN        SPT
  선택 Position       P12          P07          P31
  Position 특성       P12의 속성   P07의 속성   P31의 속성

Streamlit에서 스케줄링 방법을 변경하면서 Block의 공간적 배치가 실제로
달라지는 모습을 확인하자, 선택된 Position이 Block의 고유한 속성이
아니라는 점이 직관적으로 드러났다.

즉,

> **Position Information Table 자체는 스케줄링의 입력 데이터이지만, 특정
> Block에 연결된 '선택된 Position'은 스케줄링 방법론의 선택 결과이다.**

이 두 가지를 구분해야 한다.

------------------------------------------------------------------------

## 5. 조인이 가능하다는 것과 독립변수로 사용할 수 있다는 것은 다르다

이번 분석에서 중요한 교훈 중 하나는 다음과 같다.

> **데이터를 기술적으로 연결할 수 있다는 것과 해당 변수를 예측모델의
> 독립변수로 사용하는 것이 타당하다는 것은 별개의 문제이다.**

DDQN Result를 Mapping Table로 이용하면 Block과 DDQN이 선택한 Position을
정상적으로 연결할 수 있다.

하지만 이 연결이 가능하다고 해서 선택된 Position의 속성이 자동으로
`Block Position Cycle` 예측의 사전 독립변수가 되는 것은 아니다.

변수를 모델에 사용하기 위해서는 다음 질문이 추가로 필요하다.

> **예측하려는 시점에 이 변수의 값을 이미 알고 있는가?**

선택 Position은 스케줄링 방법론에 의해 결정되므로, 데이터 생성 순서와
예측 시점을 고려하여 변수의 역할을 판단해야 한다.

------------------------------------------------------------------------

## 6. 데이터의 실제 생성 흐름 재정리

전체 데이터 구조를 시간적·논리적 순서로 다시 정리하면 다음과 같다.

### Scheduling 이전에 존재하는 정보

-   Block Information
-   Position 후보들의 Information
-   Initial Yard State
-   Block Position Cycle

↓

### Scheduling Method

-   DDQN
-   EDDQN
-   Earliest Start Time
-   Longest Processing Time
-   Resource Utilization Based
-   Response Time Based
-   Shortest Processing Time

↓

### Scheduling 과정에서 결정되는 정보

-   Block별 선택 Position
-   배치 순서
-   Planned Start Time
-   Planned Finish Time

↓

### Scheduling 결과 비교에 활용되는 정보

-   Delay
-   Advance
-   Position 활용 결과
-   시간 및 공간 배치 패턴 등

따라서 `선택된 Position`은 Block 자체에 원래 존재하는 고유 특성이 아니라
Scheduling Method의 영향을 받아 결정되는 정보이다.

## 7. 프로젝트 분석 구조 수정

기존 구조는 다음과 같았다.

> **Block + DDQN 선택 Position + Initial → Block Position Cycle 예측**

이를 다음과 같이 분리하는 방향으로 수정한다.

### ① Machine Learning: Block Position Cycle 예측

**Block의 사전 특성 → Block Position Cycle**

목적:

> Block의 특성을 이용하여 기준 처리기간을 어느 정도 설명하고 예측할 수
> 있는가?

최종 회귀모델에서는 선택된 Position처럼 스케줄링 이후 결정되는 정보를
사전 독립변수와 구분한다.

------------------------------------------------------------------------

### ② Scheduling Comparison: 7가지 방법론 비교

**Block / Position 후보 / Initial / Cycle 등의 Scheduling 사전 조건**

↓

**7가지 Scheduling Method**

↓

**Scheduling Result 비교**

비교 대상 예시:

-   선택 Position
-   Planned Start Time
-   Planned Finish Time
-   Delay / Advance
-   Position 활용
-   공간적 배치 차이
-   시간적 배치 차이

목적:

> 동일한 입력 조건에서 스케줄링 방법론에 따라 Block의 시간 및 공간 배치
> 결과가 어떻게 달라지는가?

------------------------------------------------------------------------

### ③ Streamlit Visualization

Streamlit에서는 7개 스케줄링 결과를 공간과 시간 관점에서 비교한다.

**Scheduling Method 선택**

↓

**Block별 Position 변화**

↓

**Planned Start / Finish 변화**

↓

**방법론별 Yard 운영 결과 비교**

이 과정에서 Streamlit은 단순히 최종 결과를 보여주는 발표용 도구가
아니라, **데이터 구조와 변수 간 관계를 재검토하게 만든 탐색적 시각화
도구**의 역할도 수행했다.

------------------------------------------------------------------------

## 8. 기존 DDQN 기반 회귀분석의 처리

기존의

**Block + DDQN Position + Initial → Block Position Cycle**

분석을 반드시 삭제할 필요는 없다.

다만 이를 최종 예측모델로 해석하기보다는 다음과 같은 탐색적 분석으로
제한하여 해석할 수 있다.

> DDQN이 선택한 배치정보를 추가했을 때 Block Position Cycle에 대한
> 통계적 설명력이 어떻게 변화하는가?

이 경우에도 Position 변수의 중요도가 높게 나타났다는 이유만으로 해당
Position 특성이 Cycle의 원인이라고 해석해서는 안 된다.

최종 모델에서는 데이터 생성 순서와 실제 예측 시점에 이용 가능한 정보를
기준으로 독립변수를 다시 구성한다.

------------------------------------------------------------------------

## 9. 프로젝트에서 두 차례 이루어진 분석 가정의 재검토

이번 프로젝트에서는 분석 과정에서 두 차례 중요한 가정을 다시 검토했다.

### 첫 번째 재검토

**초기**

`Block Position Cycle = 실제 처리 결과`

↓

데이터 구조 및 관련 자료 재검토

↓

**수정**

`Block Position Cycle = 스케줄링 이전에 주어진 기준 처리기간`

### 두 번째 재검토

**초기**

`DDQN이 선택한 Position 특성 = 일반적인 회귀 독립변수`

↓

7개 Scheduling Result를 Streamlit으로 시각화

↓

동일 Block의 Position이 Scheduling Method에 따라 달라지는 것을 확인

↓

**수정**

`선택 Position = Scheduling Method의 영향을 받아 결정되는 정보`

------------------------------------------------------------------------

## 10. 발표 및 보고서에서 활용할 수 있는 서사

프로젝트의 분석 과정을 다음과 같이 설명할 수 있다.

> 초기에는 Block Position Cycle을 실제 처리 결과에 가까운 값으로
> 해석하고 분석을 시작하였다. 그러나 데이터 구조와 관련 자료를
> 검토하면서 해당 값이 스케줄링 이전에 주어진 기준 처리기간임을 확인하여
> 해석을 수정하였다.
>
> 이후 DDQN Scheduling Result를 이용하여 Block과 선택 Position을
> 연결하고 Position 특성을 포함한 회귀분석을 진행하였다. 그러나 7가지
> 스케줄링 결과를 Streamlit으로 시각화하는 과정에서 동일한 Block도
> 방법론에 따라 서로 다른 Position에 배치된다는 점이 명확하게 드러났다.
>
> 이를 통해 Position Information 자체는 스케줄링의 입력 조건이지만, 특정
> Block에 연결된 선택 Position은 스케줄링 방법론의 영향을 받아 결정되는
> 정보라는 점을 구분하게 되었다.
>
> 이에 데이터가 무엇을 의미하는지뿐 아니라, 각 데이터가 언제 그리고 어떤
> 과정으로 생성되는지를 기준으로 변수의 역할을 다시 분류하고 전체 분석
> 구조를 재설계하였다.

------------------------------------------------------------------------

## 11. 핵심 교훈

이번 프로젝트에서 얻은 중요한 분석 원칙은 다음과 같다.

### 데이터의 의미뿐 아니라 생성 시점을 확인해야 한다

컬럼의 정의를 이해하는 것만으로는 충분하지 않다.

**언제 생성되는 값인지**, **어떤 과정의 입력인지**, **어떤 과정의
결과인지**까지 확인해야 한다.

### 예측 시점에 사용할 수 있는 변수인지 확인해야 한다

독립변수 후보를 선정할 때 다음 질문을 확인한다.

> **이 값을 예측하려는 시점에 실제로 알고 있는가?**

### 기술적으로 Join이 가능하다고 분석적으로 타당한 것은 아니다

테이블 간 Key를 찾아 데이터를 연결하는 것은 데이터 가공의 문제이고,
연결된 변수를 모델의 독립변수로 사용할 수 있는지는 별도의 분석 설계
문제이다.

### 시각화는 결과 표현뿐 아니라 분석 검증에도 사용될 수 있다

이번 프로젝트에서는 Streamlit 시각화를 통해 Scheduling Method에 따른
Position 변화를 직접 확인하면서 기존 분석 구조의 문제를 발견했다.

따라서 시각화는 단순한 결과 전달 수단이 아니라 데이터의 구조와 분석
가정을 검증하는 도구로도 활용할 수 있다.

## 12. 최종 프로젝트 구조

**1단계 --- Cycle Prediction**

`Block 사전 특성 → Block Position Cycle`

↓

**2단계 --- Scheduling**

`Block + Position 후보 + Initial + Cycle → 7가지 Scheduling Method`

↓

**3단계 --- Scheduling Result**

`Position / Start / Finish / Delay / Advance 등`

↓

**4단계 --- Streamlit Visualization**

`7가지 방법론의 공간·시간 Scheduling 결과 비교`

이 구조를 기준으로 기존 전처리, 회귀분석, Scheduling 비교 및 Streamlit
시각화 코드를 전면 재검토한다.
